# Comfy-Org/ComfyUI issue 16604: does the ref-row mismatch reproduce here? (2026-09-29)

Board direction `comfy-16604-ref-rows`. CPU only, nothing in core touched.
Probe: `bench/probe_ref_rows_16604.py`; case table: `2026-09-29_ref_rows_16604.json`.

## The report

`MiniMaxH3ReferenceToVideo` fails in `MiniMaxH3Model._forward` at
`all_video_rows[~img_update] = cond_video_rows`: the value has the reference row
count and the indexed result has the whole video segment's row count. The
reporter's table brackets it between a packed sequence that works and one that
fails near 16384 rows, and suspects an index or buffer limit, or a layout
reused after the references changed. The reporter opened the issue on
2026-09-27 and closed it as completed the same day with no comment
(`gh api repos/Comfy-Org/ComfyUI/issues/16604`), so the cause was not stated.
Their setup was ROCm, a fused ref-delta INT8 checkpoint and a third-party
sparse-attention node whose bypass test was still pending.

## Result on this checkout: does not reproduce

The probe builds the layout the way `extra_conds` does, builds the condition
rows with core's own `_cond_video_rows`, and runs the same mask assembly as
`_forward`. For every case the count of rows `~img_update` selects equals the
count of condition rows, and the assembled tensor puts each row where the layout
says. Cases: the report's four table rows (including the two it says crash),
1344x768 at 345 frames with one and with three image references, an image plus a
video reference at 1152x768, and a keyframe plus a reference. The largest packed
sequence is over 100000 rows (`seq_len` in the JSON), far past 16384, so there is
no threshold in the layout or in CPU boolean-mask assignment.

Controls, both must fail and do:

- a layout built for one reference and run against another reference's latent
  (the stale-layout hypothesis) raises a shape mismatch of the same form as the
  report;
- `img_update` inverted (reference rows True, video rows False) raises the
  report's exact form, with the indexing result equal to the video row count.

That second control is the useful one: the report's counts are what an inverted
`img_update` produces, so if the failure is real the thing to look at is where
the mask comes out inverted or wrong on that stack, not the layout's length.

## What this does and does not show

- The layout is correct at every size tested, on the CPU.
- The stale-layout route is not reachable through `extra_conds`: the layout and
  `cond_video_latents` are both built there from the same `minimax_refs` and
  `minimax_keyframes`. `_forward` rebuilds a layout only when the signature
  `(text_len, latent_t, lat_h, lat_w, audio_t)` differs, and that signature does
  not carry the references, so a layout would go stale only if something replaced
  the payload's `refs` or `cond_video_latents` after `extra_conds` ran. A grep of
  core and this pack (`cond_video_latents`, `minimax_refs`, `minimax_payload`) finds
  writers only in `extra_conds` and the two nodes that build `minimax_refs`.
- Not tested: CUDA and ROCm device execution of the mask assignment (this probe
  is CPU; the card was not used), the reporter's checkpoint, and the reporter's
  version (this checkout's `comfyui_version.py` is 0.37.0; the report names 0.37.4
  and 0.33.2, so the model file may differ). The reporter's third-party node is
  the more likely place for a changed mask, unverified.
- One thing to check in this pack, not in core: `_compile_reference_records` in
  `reference_conditioning.py` builds `minimax_refs` too. Its image branch takes
  the grid from the VAE's actual latent (and warns if it differs from the pixel
  size over 16), but its video branch sets `latent_h` and `latent_w` from
  `canvas // 16` and does not read the latent's shape. If a VAE returned a
  different grid for a reference video, the layout's row count would differ from
  `patchify_video`'s and the assignment would fail with this report's message.
  Not tested; it would need a stand-in VAE output of another shape.
